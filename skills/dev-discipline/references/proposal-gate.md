# 修改提案与批准门

任何修改（代码 / DDL / 配置 / 数据清理 / 删资源）在动手前必须有四段式提案。这不是形式主义——真实事故里，一次没有依据的 DDL 差点在共享工作树污染下获批，一次"看起来无害"的清理删掉了无法证明归属的镜像。四段式是让提案者和审批者都能在动手前看到全貌。

## 四段式模板

```
【改什么】精确到文件/表/键/行级，一份提案只做一件事
【依据】生产实测数字 / 已定案文档编号 / 测试结果——不能是"应该是/我推断"
【风险】谁会被影响？最坏情况是什么？哪些前提可能不成立？
【回滚】回滚点在哪（.bak/备份+校验和）？回滚动作是什么？回滚本身验证过吗？
```

**依据的等级**（从高到低）：

1. 刚刚在生产/真库实测的数字（附命令与输出）
2. 已定案的文档编号（如"依据 docs/xx 第 n 条定案"）
3. 本地测试结果（附测试命令与通过数）
4. 推断——**不合格**，先去实测

## 哪些操作必须等明确批准

- 生产任何**写**操作：UPDATE/INSERT/DELETE/DDL、改配置、写文件
- 删数据、删资源（磁盘清理、镜像清理、旧文件）
- 重启生产服务 / 重建容器
- 杀非自己启动的进程
- 花钱操作（云资源、API 配额）
- push 到远端仓库、覆盖共享文件
- 任何"做了难回头"的动作

**放行标准 = 用户明确说「批准 / 执行 / 可以开始了」，或点选含批准字样的选项。**

疑问句不是授权。用户说「现在能执行并验证吗？」「这样可以吗？」是在探询，此时正确动作是：给出方案 + 风险 + 需要的授权范围，然后等。曾经把用户的一句疑问句当放行直接跑了生产 DDL，被权限层拦下——那是侥幸，不是流程。

同理：一次批准不覆盖下一次。"上次你让我删过悬空镜像"不等于"这次也能删"。

## 反证检查（不可逆动作必做）

提案方的汇报不能是唯一证据（历史上一次基于被脏工作树污染的预检的 DDL 提案差点获批）。执行前自问三问并写进提案：

1. **我的结论依赖哪些前提？**（如：工作树干净、生产 schema 就绪、无并行会话在改同一文件）
2. **哪个前提可能错？**逐个用一手命令验证（如 `git status -- <涉事文件>` 能让他人未提交改动当场现形）。
3. **我没看什么？**（哪个日志、哪张表、哪个消费端没检查？）

关键事实由只读通道独立复核（新会话或独立脚本从生产一手取数），不引用提案方转述。

## 删除类操作的两个前置证明

删共享环境里的任何资源，"无引用"和"归属我方"是两个命题，**必须分别取证**：

- **无害性** = 没有任何现役容器/服务/重启路径引用它
- **归属权** = 部署台账 / 构建指纹 / 时间谱系能证明是我方产物

共享宿主上多项目共存时，悬空镜像、构建缓存天然是公共产物——"尺寸日期像我们的"只是弱证据。缺归属证据的按"疑似他人"保留，或连证据一起请批。全局池资源（builder cache 等）动手前先向用户言明全局性质。

## 提案被拒/被问之后的姿势

- 用户追问「确定吗？」≠ 要求重申立场，而是要求新证据。回去拿一手数据。
- 被拒后不得换个说法再提同一方案（sneaky re-approval）。
- 用户给出了业务侧信息（截图、口头数字）与你的数据矛盾时，**优先怀疑自己的查询域**（分页、时间窗、会话态），翻案往往发生在用户拿截图反问之后——把用户的常识当对账的一环。
