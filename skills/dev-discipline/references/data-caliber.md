# 数据口径与管道纪律

背景：系统从多个外部平台（API/OAuth/人工维护表）拉数据进本地库，再投影成看板。这个形态下最贵的错误是**静默的部分视野**：管道天天 success，但某个账号/服务包/字段从来没进过系统，直到用户拿业务权威数字对账才暴露——历史上一个 22% 的覆盖率缺口上线一个多月无人发现。以下纪律全部为堵这个洞。

## 外部 API 指标上线三步，缺一不可

1. **拉通**：接口能拉到数据，回填跑通；
2. **对账覆盖率**：与业务权威总数（人工维护的权威表/平台后台总数）逐格对，差异能分解闭合；
3. **业务不变量落每日审计**：如"总量 A ≥ 分量 B"这类常识性恒等式，机器每天自动验。

"回填跑通" ≠ "覆盖全了"。**审计 FAIL 的处置只有两种**：修复，或给出两边口径定义 + 差值分解后定性——不得以「口径分歧」名义长期挂起（历史上一个天天 FAIL 的对账项被挂一个月，实为覆盖率缺口）。

同一页面并排展示不可比口径的指标，必须标注口径。写进文档的口径必须逐页对到取数代码（哪个函数、哪张表、什么过滤）——不读码不落笔。

## 口径分歧的排查姿势

- 报"口径不一致/数据异常"前，先 DB 实证各页面**真实读取**的表和数值——表名、注释、前端文案都可能骗人（幽灵表、无人读的旧表、文案过时）。
- 两边数字对不上时：先证伪自己的假设再定案；差值要逐格分解到具体键（哪个账号/包/日期），精确闭合。
- 口径切换（如"实付→应扣"）要登记切换点：切换点前后的数字不可混比；切换当日的锚点全部重算。
- 用户的业务常识与系统输出矛盾时，优先怀疑系统覆盖面，而不是"口径不同"合理化。

## 管道与镜像类高频坑

**「job success 但 0 新行」是最高频的静默故障形态。**同步任务失败被 try/except 吞掉、上游返回空、区间查询语义不对、循环中断后无人重试——日志全绿，数据没进。防线只有**新鲜度检查**（表级 max 日期哨兵），每条管道都必须挂。

- **失败必须落运行记录**（不能只打日志）；记录要落在监控真的在读的库里——跨库系统里，job 写 A 库的记录、哨兵盯 B 库 = 结构性失明。
- **分页接口拉到空页**才算拉全（服务端无视 limit、固定页大小是常态）。
- **全量替换型任务**（DELETE+INSERT / TRUNCATE+COPY）终态行数用全部表处理完后的一次性 count 校验；`TRUNCATE CASCADE` 是 DDL 级联，关 FK 检查的 replica 模式拦不住它——逐表独立事务的全量替换用 `DELETE FROM`。
- **UUID/ID 跨环境共享假设必须写明适用范围**（仅同源 seed）；生产侧会新建的实体（账户/SKU/代理）一律按业务键重映射兜底。
- **白名单映射的丢弃分支必须可观测**（落审计/计数），不许静默 `continue`——历史上一个服务包因白名单不认识被天天静默丢弃数月。
- **映射兜底要警惕**：`"ai"` 这种模糊兜底会把无关数据误挂到已有类目上，错得悄无声息。
- **脏数据两手抓**：源头守卫（写库前丢弃未来日期/非法值）+ 存量清理，只做一头会复发。
- **每日全量覆盖的镜像机制**：本地手插的行次日会被洗掉，补数必须配自愈重填；新账户要先建档，否则镜像 FK 过滤静默丢弃。
- **cron job 三问**：那时刻关机了怎么办（要启动补跑）？失败落记录了吗？记录落在哪个库？
- 凭据错误第一时间禁用该源（防反复撞登录锁号），核实后再启用；凭证类寿命（cookie/session ~2 天）要在部署清单里检查剩余寿命。
- 派生口径选字段前**实证覆盖率**（`count(*) filter (where 字段命中)`）——"稀疏"和"全空"是两回事；跨表事实要显式桥接，别指望主表字段有值。

## 哨兵/审计设计原则

- 哨兵自己也是代码：异常分支（源不可达/0 行/空列表）必须有测试；探针上线时必须在**生产真实路径**上真跑一次看走的哪个分支——历史上哨兵探针被 301/证书问题挡住，永远走"跳过"分支出 PASS，结构性失明。
- 计数制检查有假阴性：总数达标可能被"停用账户的零行"顶满——关键缺口检查用**逐活跃单元核对**（逐账户/逐主体），报"活跃但缺行的单元数"。
- 对账哨兵窗口别太短（3 天窗口会让历史缺口滑出后永不再检）——加滚动长窗第二道。
- 哨兵输出FAIL时先判读已知家族（时差/口径/源侧停更）再升级，但"已知"必须有定案记录，不许无限挂起。
- 检查结果落库时注意：run 整体状态和单个检查状态解耦（一个软差异不该把整班拖成 failed 掩盖其他信号）。

## 对账方法论

- **双 oracle**：平台官方 API 与人工权威表互为对照；裁决者分三类（平台官方 / 人工权威表 / 业务语义不变量），前两类自动化比对，第三类异常触发人工。
- 独立复核不复用同步层代码（复用会继承它的 bug）；写独立解析器。
- 时间戳语义先验证（毫秒戳按哪个时区取日期，UTC 取差 8 小时=全表偏一天的假差异）。
- 钉在锚点上的对账：先在本地/小窗复算，再决定要不要在生产跑（容量纪律优先）。
- 归属/合并类对账要看**派生元组**，不只看事实行（见 verification.md 穿透原则）。
