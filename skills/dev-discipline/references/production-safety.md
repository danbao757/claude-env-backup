# 生产操作安全

背景：生产是低配资源上跑着真实业务的系统（数据库可能只有百 MB 级缓存、宿主机内存被多个容器瓜分），且生产是**文件同步部署、多会话并行操作**——你在终端里看到的"现状"随时可能过期。这里每条规则都有一次真实事故背书：一条"只读"百万行 JOIN 冻死过整台服务器；一次容器内 monkeypatch 把生产配置里的多租户凭证抹掉断流三个班次；一次 `up -d` 静默没重建容器，旧进程跑了半天旧代码。

## 容量评估（一切生产操作的前置，含只读）

执行前先过一道检查：**当前系统状态和容量能不能支撑这条命令？**（内存余量、负载、容器水位 vs 该操作的资源代价）

- **有冻结/卡死风险的操作，先征得用户同意**：大表聚合/JOIN/全表扫描（尤其百万行级）、大批量日志扫描、并发搬运、压测、任何让低配数据库重算力的 SQL。
- 判断顺序：**先查表规模/数据量 → 再决定查询姿势**（小窗、分步、LIMIT、先 EXPLAIN），重姿势一律降级为请批项。
- 轻探测豁免（秒级零负载，不需请批）：容器列表/资源占用、单行 SELECT、tail 日志尾、健康端点、ping。
- "只读"不是免检标签——只读照样吃 CPU/内存/锁。

## 进程与服务操作

- **杀进程只能按 CommandLine 精确匹配**目标脚本/参数，绝不按进程名一刀切（`uv.exe` 可能是后端的父进程，`python.exe` 可能是别人的任务）。查询进程时排除诊断命令自身（查询串里含关键词会把自己匹配进来）。
- **服务死活只信健康端点**（curl /health），不信任务状态、不信进程列表——子进程可能脱离父任务仍在跑，反之端口被孤儿进程占着新进程起不来。重启前先确认端口占用。
- 长耗时任务（>10 分钟）不塞进交互式 shell（会话结束杀进程组）：移交用户终端、注册计划任务、或后台守护。手动触发同步类接口时 curl 超时给足（停摆后首班=大回拉，比常规班慢一个量级）。
- 「班一直 running 不结束」先查锁持有者（如 `idle in transaction` 的悬挂连接持有 advisory lock），terminate 持锁连接即恢复——先查锁再下"卡死"结论。

## 重启纪律

- **重启已知会自触发重活的服务前，先拆除触发源**（禁补跑/砍队列历史深度/摘账户）。"重启后错过的定时任务立即补跑"是默认会发生的事——资源帽是第二道防线，不是保险栓。
- 向用户交风险评级时区分「实证」与「判断」——评级错了等于误导批准。
- compose up/recreate **一律 `--no-deps`**（只动目标服务）：依赖调和会因别的容器配置漂移让整个 up 静默中止，或把无辜容器拖进重建。
- **up 后必须断言**：容器镜像 ID == 刚构建的镜像、启动时间已刷新。no-op 也会报成功。

## 单文件热更 / 部署固定姿势

1. 生产侧先留回滚点（`cp xx xx.bak-日期`）；
2. 拉生产当前版本与本地 diff，**逐 hunk 清点**（哪些是目标改动、哪些是夹带的他人改动）——在基线上打纯补丁，不直接传工作树文件；
3. **目标环境 import 冒烟**（`docker exec <容器> python -c "from xxx import yyy"`）——md5 只证文件传对了，不证能跑；
4. 切换后盯启动日志到完成。
5. 跨来源比文件一致性先统一换行符（CRLF/LF），否则 hash 全军覆没假"不一致"。
6. 前端静态资源部署=就地覆盖，**严禁 mv 目录/删目录重建**（web 容器的 bind mount 钉死在目录 inode 上，换目录后永远喂旧版且无任何报错）；验证从浏览器侧做。

## DDL 与配置

- DDL 先执行，引用它的代码后部署（顺序反了 = 上线即炸）；执行前后登记台账（失败也必须记）。
- **避开业务高峰**：no-op 的 `IF NOT EXISTS` DDL 照样拿 ACCESS EXCLUSIVE 锁，白天与业务查询死锁过。schema 已就绪的环境跳过"补差 DDL"前置步骤，直调核心函数。
- **生产容器/进程内跑触发或诊断脚本，严禁 monkeypatch 共享模块函数**——你 patch 的读路径过滤器，同进程的配置写回路径也在调它，跑完配置就被抹了。要收窄行为用调用点级包装（try/finally 立即还原）或白名单参数；跑完核对配置关键键数没变。
- **打印任何 config/token/凭证类字段前先脱敏**（删凭证键再输出，或只打键名+长度）。凭证永不进对话。
- 不可逆三禁：绝不 `down -v`（删卷）、绝不未经同意 push 远端、绝不覆盖生产 .env/网关配置。

## 多会话并行协调

- 动生产前**读操作台账尾**（别的会话最近部署/改了什么），尊重部署软锁，不抢。
- 共享工作树上有他人未提交文件时，**绝不 `git add -A` / 全树部署**——只动自己那几行、只部署显式指定的文件。
- **任何会话部署过，其余会话对上线状态的认知全部作废重核**：判断"某改动是否已在生产"以生产一手证据为准（线上版本接口 + git merge-base 祖先关系；后端=台账尾+镜像 tag）。
- 并行会话构建的产物必然带上分支里一切已提交改动——"我没部署过"≠"没上线"。

## 内存与大数据

- 外部大文件解析一律**流式**（stream + 逐行/分块），禁整文件载入；要整载的加字节护栏拒收超限。
- **超限宁可抛错留队列重试，不可截断**——聚合语义下截断 = 写入部分和的错数据，比失败更糟。
- flush/落库后立即弃 payload 引用——"返回值从来没人消费"的路径干脆别累积。
- 攒批大小按「单条最大体积 × 上限」做内存预算，别按条数拍脑袋。
- 跨环境搬数据：显式列名（列序可能不同）、FK 按名字重映射（UUID 命名空间可能不同）、大文件先 gzip 再传输（管道流会静默断）。
