# 个人开发纪律

这套纪律几乎每一条都来自一次真实事故：整台服务器被一条"只读"查询冻死、数据缺口静默存在数月才被用户拿业务常识戳穿、临时脚本把生产配置抹掉、哨兵天天报绿其实从未真正检查过……它们共同的根因不是能力不足，而是「看起来没问题」和「验证过没问题」之间的差距。本技能的职责就是把这个差距关掉。

本项目里钱和真实业务数据在系统里流动，"差不多的正确"就是错误。宁可多问一句、多等一班数据，不可带着推断宣布完成。

## 核心信条

违反任何一条，其余工作全部作废：

1. **无证据 = 未完成。** 任何「已完成」都要附可复现证据（命令输出 / DB count / 截图 / 测试结果 / 线上版本号）。验收结论只写有证据的。
2. **只读 ≠ 无害。** 只读查询照样吃 CPU/内存/锁。资源紧绷的系统上，一条百万行级 JOIN 聚合就能冻死整机。生产上任何操作先过容量评估。
3. **提问 ≠ 批准。** 用户说「现在能执行吗？」是在权衡，不是放行。生产写操作的放行标准 = 明确的「批准/执行」字样或选项点选；疑问句、反问句一律视为在咨询。
4. **表象 ≠ 故障。** 看到失败日志 ≠ 管道坏了（可能是正常噪声）；看到 0 行 ≠ 数据丢了（可能是镜像环节自己清掉的、T+1 还没到、查询姿势不对、或分页只拉了第 1 页）。先搞清数据实际走哪条路、看的域完不完整，再下结论。
5. **「本地 = 生产 + 我的改动」不成立。** 共享工作树、并行会话、未部署的提交随时污染这个假设。判断「生产在跑什么」只信生产一手证据（容器内实际文件 / 镜像 ID / 启动时间 / 线上版本接口），不信 git 状态，不信「我没部署过所以没上线」。
6. **验证穿透到最终消费端。** raw SQL 聚合对了 ≠ API 输出对了 ≠ 页面显示对了；文件是新的 ≠ serving 进程是新的。改到哪一层，就验证到那一层的真实出口。
7. **负结论必须复核产生机制。** 一切「0 / 不在 / 找不到 / 为空」的结论，先复核它怎么产生的：工作目录漂移了没、命令返回码、stderr 是不是被 `2>/dev/null` 吞了、路径对不对。换绝对路径复跑一次再落笔。
8. **犯错必沉淀。** 每次事故提炼成教训条目入项目清单，只增不删。下次同类操作前对照相关条目。提问不等于批准，用户点头过一次也不等于永久授权。

## 使用流程

### ① 开工（新会话/新任务第一步）

1. **三读**：项目 CLAUDE.md（环境事实+铁律）→ 教训/复盘清单 → 最新交接/待办文档 + 部署或操作台账的尾部（看别的会话最近干了什么）。
2. **多会话意识**：并行的其他会话可能已经部署、改库、改配置——开工时对「现状」的任何记忆都要重新对账。别人部署过前端 = 我此前对上线状态的认知全部作废重核。
3. **确认环境事实**：时区（容器日志/同步记录常是 UTC，业务时区换算后再判断窗口）、数据源的结算延迟口径（T+1/T+N 是常态不是故障）、部署方式（git 部署还是文件同步）。
4. memory 和文档会过时：记录里挂着的「待办」可能早被修掉，先查代码/数据现状再动手。

### ② 动手前：修改提案四段式

任何修改（代码 / DDL / 配置 / 数据清理）提案固定四段：

> **改什么 → 依据 → 风险 → 回滚通道**

- **依据**必须是实测数字 / 已定案文档编号 / 测试结果——推断不能当依据。
- 生产写操作、删除、DDL、杀进程、花钱操作：**先提案，等批准**。
- 不可逆动作执行前做**反证检查**：「我的结论依赖哪些前提？哪个可能错？我没看什么？」

细则与模板：[references/proposal-gate.md](references/proposal-gate.md)

### ③ 执行中：验证链

- 每类改动有固定完成判定顺序（编译检查 → 重启/确认热重载生效 → 接口实测 shape → DB 实证数值 → 浏览器 0 报错），缺一环不算完。
- 用**锚点对账**：改动前记录关键数字（金额/行数/版本），改动后逐一复核分毫不差。
- 防范静默失败家族：吞错、fire-and-forget、白名单静默丢弃、"success 日志 + 0 行"。
- 拿不准的结论，先读 [references/verification.md](references/verification.md)。

### ④ 收尾（任务完成不等于会话完成）

1. 更新进度权威文档 + 交接文档 + 记忆；**同步纠正所有引用旧结论的文档/索引**（不留僵尸表述）。
2. 对比用的基线数字当场写入持久层（数字 + 时刻 + 口径三要素），不能只留在对话里。
3. 留**验证钩子**：T+1 类问题必须跨班验证（"明早核什么"写清楚），当天转绿可能是假阴性。
4. 新教训入清单。交接文档按三档组织：一档我方待批执行包 / 二档用户或业务侧动作 / 三档观察项。

细则：[references/session-rhythm.md](references/session-rhythm.md)

## 动手前 30 秒自检（通用版）

- [ ] 我要下的结论，是用 DB/接口/日志**验证**过的，还是从表象推的？负结论复核过产生机制吗？
- [ ] 这个修改的四段式齐了吗？依据是实测还是推断？
- [ ] 用户的话是疑问句还是明确指令？这步需要批准吗、拿到了吗？
- [ ] 碰生产（含只读）：容量评估过了吗？这一步有没有冻结/卡死风险？
- [ ] 这条命令会跑多久？>10 分钟的长任务移出交互通道。杀进程按 CommandLine 精确匹配了吗？
- [ ] 改完的完成判定链是哪几步？验证穿透到最终消费端了吗（SQL→API→页面）？
- [ ] 时区、时间窗、T+N 结算延迟想过了吗？定时任务密集窗避开了吗？
- [ ] 回滚点留了吗（.bak / 备份 + 校验和）？回滚通道验证过吗？
- [ ] 判断"不存在/为 0"前：分页拉到空页了吗？看的是完整响应体还是前 N 个字符？
- [ ] 要写进文档/记忆的结论，证据齐了吗？会取代哪条旧结论、一起改了吗？

## 本技能的边界

- 这里是**跨项目通用**的纪律。项目专属的环境事实（服务器、路径、表名、班次时刻）以各项目 CLAUDE.md 和交接文档为准，两边冲突时以更严者为准。
- 敏感信息（IP、凭证、token、内部人名）永远不出现在技能、对话或文档正文里。
- 这套纪律不是官僚流程：如果某个步骤对这个改动确实无意义，说明理由后可以裁剪——但核心信条（证据、批准门、容量评估、穿透验证）不可裁剪。
